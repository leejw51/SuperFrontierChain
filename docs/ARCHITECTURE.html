SFC architecture

Super Frontier Chain is an MIT-licensed Rust blockchain framework. Its current runtime is a development sequencer with independently replaying followers. It executes Ethereum contracts using REVM and synchronizes through Cap’n Proto RPC, with TCP as the default loopback transport and HTTP/3 for TLS/QUIC peers. See quickstart for operating commands and protocol for the wire interface.

See the 2026-10-20 review for verified fixes, determinism evidence, production design gaps, the CometBFT/SDK direction and MLX assessment.

Default direct TCP uses the same service and is loopback-only and unencrypted. node: explicit development sequencer or replaying follower. rpc: bounded HTTP JSON-RPC requests/batches and read-only EVM simulation.

Runtime boundaries

The Rust node owns execution, admission, persistence, HTTP JSON-RPC, peer RPC, and the bundled dashboard. Python is process tooling only. A current-thread Tokio runtime with a LocalSet runs Cap’n Proto's local futures and asynchronous network I/O. Blocking execution/storage work is dispatched to blocking tasks where used; shared mutable node state is guarded by a mutex. Ordered admission and state mutation still use that lock. Peer block reads use bounded blocking workers and shared storage snapshots; SQLite catch-up also reads snapshots without acquiring the execution mutex.

The selected CPU/GPU/HYBRID backend handles independent transaction signature recovery (GPU by default). CPU parsing uses ordered Rayon work; all modes preserve input order; EVM execution and durable state mutation remain sequential. A block contains a deterministic ordered transaction list, not parallel state writes. Block execution and admission batches reuse one REVM handler while resetting transaction-local state. Pure HTTP submission batches share this path; mixed RPC batches retain ordered per-request dispatch. Followers omit the unused pending EVM cache, but still independently execute and verify every imported block.

Transaction lifecycle

View Mermaid source
flowchart TB
    Signed[Signed Ethereum transaction bytes] --> Verify[Check encoding, signature and chain ID]
    Verify --> Queue[Check nonce and balance; enqueue]
    Queue --> Execute[Block scheduler executes selected transactions]
    Execute --> Build[Build state root, block and receipts]
    Build --> Commit[Commit state and head with synced WAL]
    Commit --> Publish[Expose receipts and blocks to readers]
  1. A client submits signed Ethereum bytes over HTTP JSON-RPC or peer RPC.
  2. Admission validates encoding, chain ID, signature, nonce, balance, and resource limits, using a cached pending EVM state.
  3. The sequencer's 100 ms timer selects pending transactions in order and executes a candidate block. Reverted contract calls can be included with failed receipts; invalid transactions are dropped during local selection.
  4. The application computes its state commitment and builds receipts and the block.
  5. One durable RocksDB batch commits account deltas, metadata, block, head, and receipt indexes. The node updates its in-memory head and pending cache.
  6. Maintenance appends the Cap’n Proto projection and prunes expired history.
  7. Followers request blocks, independently replay them, compare roots, and commit.

The timer skips missed ticks; 100 ms is a configured target, not a guaranteed latency or finality SLA. Block timestamps are integer seconds.

Framework extension points

Application::with_module registers uniquely named Module implementations. begin_block and end_block run in registration order around EVM execution and can update application state. Hooks must be deterministic across nodes. Candidate execution works on a cloned state so an error before persistence does not commit a partial application transition. Cross-chain, staking, governance, and bridge modules are outside the implemented scope.

Operations and observability

make start uses scripts/service.py to manage one release node in the background. A process-held file lock and private Unix socket provide ownership and stop control. It initializes a new default config when needed, waits for HTTP readiness, and cleans up failed starts. make stop requests graceful shutdown and escalates after ten seconds. The service does not automatically restart a crashed node.

make testnet instead uses scripts/supervisor.py: one sequencer and N−1 followers, shared genesis, individual state directories and TLS identities, separate Cap’n Proto logs, and bounded crash restarts with backoff. Its manifest and status file are local process-management records, not consensus state. Both managers use Python's standard library on macOS/Linux.

The dashboard is static HTML/JavaScript embedded in the Rust binary and served at /dashboard on the Ethereum HTTP listener. /dashboard/stats reads at most 61 blocks to calculate a recent committed-TPS window and mean block interval. It also reports head, retention, pending count, state account count, and configured upstream. Polling is every two seconds with an explicit stale-data state. It does not measure peer count or follower lag. No additional frontend server or build is needed.

Structured runtime events are stored as length-framed Cap’n Proto in data/logs/node.capnp. Process managers append readable stderr to node.log. Logs are not automatically rotated. Runtime logging is best-effort and separate from durable blockchain records. Dashboard APIs return application/x-capnp; the bundled browser decoder restores typed values for display.

Trust and failure model

The node does not use consensus votes to choose blocks. Followers trust a configured sequencer's TLS identity and re-execute its blocks; this is not Byzantine consensus. A malicious trusted sequencer could choose a different valid history. Multi-validator finality needs a reactor, durable lock/WAL recovery and adversarial network validation. Do not equate the tested consensus library with a deployed consensus network.

State execution occurs before persistence. A commit writes changed accounts, state metadata, block, head height and transaction indexes atomically with WAL sync enabled. If Cap’n Proto maintenance fails after a commit, the sequencer stops; restart reconstructs the projection from committed records. No automatic acceptance of unverified snapshots. Mempool contents are volatile; a submitted transaction is not durable until mined. Admission validates exact sequential nonces; replacement and nonce-gap queues are not implemented. Contract reverts are included with failed receipts and charged gas.

The application and DB use deterministic SFC commitments, not Ethereum's trie roots. Timestamp fields exposed to the EVM are integer seconds. At 100 ms cadence adjacent blocks can share a timestamp. Development PREVRANDAO is zero; it is not randomness.

Resource bounds

Raw transaction: 128 KiB. Raw block transactions: 2 MiB. Raw pending pool: 64 MiB. HTTP request: 5 MiB; JSON-RPC batch: 4,096 items. Peer connections: 32. QUIC concurrent bidirectional streams: 8. RPC reader nesting and traversal are bounded. Sync requests return at most 64 blocks and stop near 2 MiB raw transaction payload. These are resource bounds, not a complete public-network DoS defense. Listeners are local only.

Remaining scaling work

State commitments update an incremental Merkle Patricia trie. EVM preparation, change detection and world-map cloning still scale with current state size. Startup projection repair is linear in retained history and currently builds it in memory. Large states and long archives still need reduced state copying and streaming repair. Cap’n Proto is not an independent import format yet. The selected verifier recovers independent transaction signatures. JSON-RPC batch authentication runs without holding the state mutex; ordered admission, EVM execution and state queries still use it. Imported blocks verify signatures in parallel before sequential replay. Parallel EVM execution is deferred until deterministic conflict handling is proven. Indexed collection preserves result order, and a strict block batch reports the first invalid transaction in input order regardless of worker count.

RocksDB journaling

Every state/pruning batch and every signing-guard update uses WAL-enabled, synchronous writes. A block's account deltas, metadata, head, history and receipt indexes share one atomic WriteBatch and one WAL synchronization; there is no per-transaction journal sync. Cap’n Proto remains a recoverable history projection, not the transaction journal.

History appends reuse an open segment and borrow the committed block bytes. The projection syncs at segment rotation and clean close. Periodic projection fsyncs were removed after measurements showed contention with the durable WAL; the investigation records the evidence and remaining throughput variation. A partial append is truncated before retry. A crash may lose projection bytes, but restart rebuilds them from the already-synced retained RocksDB blocks. No consensus format or authoritative WAL policy changes are involved.

WAL files are native binary *.log files in the RocksDB directory (data/rocksdb for the chain; the caller-selected directory for DurableSigner). RocksDB manages their rotation and removal after records reach SST files. The configured pruning policy applies to logical chain history, not directly to WAL file ages. Archive mode preserves logical history without forcing RocksDB to retain obsolete WALs.

Recovery uses AbsoluteConsistency: detected corruption or a torn record prevents startup. No automatic record skipping or database repair is attempted. This favors refusing to start over silently rolling back a chain head or forgetting a signed vote; a damaged journal requires operator recovery. Normal intact WALs replay automatically.

make test-journal starts a writer subprocess, acknowledges a block and signed vote, then kills it without closing either database or exporting the block to Cap’n Proto. The test verifies that no SST files exist, reopens through WAL recovery, checks the state/head/receipt index, repairs Cap’n Proto, and confirms double-sign protection survives. A separate checksum-corruption test verifies that both database types refuse startup. These tests simulate a process crash, not physical power loss or faulty storage.

Retention lifecycle

Pruning is enabled by default with a 60-second window. Expiry uses the committed head timestamp and is exclusive: a block exactly at the cutoff remains. The head is always retained. Pruning deletes historical block records and associated receipt indexes while keeping current account/code/storage state. EVM's recent block-hash context remains part of current state.

Pruning runs on open and after production/import. Large backlogs are deleted in WAL-synchronized batches bounded by 256 blocks or roughly 8 MiB of delete operations, checked after each block. A restart resumes from remaining records. Expired whole Cap’n Proto segments are removed; pruned segments span min(retention_seconds, 60) seconds and archive segments span one hour. A boundary segment may retain less than one extra segment until rotation, and restart reconstructs the exact retained projection. RocksDB compaction asynchronously reclaims physical space.

Archive mode disables history pruning. Switching back to archive preserves only remaining and future history, not deleted records. Archive history is not a set of historical EVM state snapshots. A follower whose next required block is pruned must use an archive peer; automatic snapshot synchronization is not implemented.

Determinism contract

SFC-owned core collections use BTreeMap, BTreeSet, Vec, and VecDeque. Mempool duplicate lookup uses BTreeSet; the queue defines transaction ordering. OrderedDb backs EVM accounts, code, storage, and block hashes with ordered maps. REVM's returned account and storage changes are sorted before application. World serialization and state commitments use ordered maps, while receipts and logs preserve execution order. CPU/GPU/HYBRID results are collected in input order; state mutation never follows completion order. The native Metal kernel uses exact integer modular arithmetic. See backend validation and limits.

Admission uses the last committed block timestamp. Production/replay receive an explicit timestamp; the CLI samples wall time for new local blocks and genesis. Logs also use wall time, and dashboard rates use floating point; neither affects state commitments. Execution arithmetic uses integer EVM values. PREVRANDAO is fixed to zero. Custom module hooks must not read clocks, random sources, network, filesystem contents, environment variables, or unordered iteration to choose state. The hook interface itself cannot enforce purity.

This is an SFC-core guarantee, not a claim that dependencies contain no hash maps. REVM internally uses hash-based execution state. The adapter canonicalizes that state at the boundary and never uses its iteration order to choose transactions or construct commitments. Replacing REVM internals would require a separate dependency fork and verification effort. The current adapter is tested for insertion-order invariance, absent reads, zero-slot removal, creation, and self-destruction; existing worker-count tests compare serial and parallel execution results. A source regression guard rejects unordered collection and ambient clock/random identifiers in owned core modules. These tests are evidence, not a formal proof of all EVM behavior.
