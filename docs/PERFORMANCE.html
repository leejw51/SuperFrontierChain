Performance measurements

Current stress runs retain only 5 seconds of block history by default (STRESS_RETENTION_SECONDS=5, or sfc-bench run --retention-seconds 5). This applies to reused stress homes too. SQLite history remains append-only and is not pruned. Background block deletion and physical compaction can lag the logical cutoff; current state, head and the cutoff boundary remain available. The dated measurements below retain their stated retention windows; the latest longer comparison explicitly uses 60 seconds to match the sustained-throughput goal.

Latest native MLX/Cap’n Proto investigation: projection sync stalls, indexer isolation and dispatch tuning. The dated comparisons below retain their original workloads and persistence policies.

Latest GPU enhancement: cooperative recovery, paired TPS and CPU measurements.

Original node backend comparison: CPU/GPU/HYBRID TPS and CPU usage. The signature-recovery microbenchmarks are separate from committed network TPS.

Current SQLite candidate and 60-second validation (2026-10-24)

The retained candidate uses SQLite schema 5 (compact binary keys and ascending address indexes), 128-row INSERTs, memory-backed temporary journals and a checkpoint gate that reserves a writer-idle interval after COMMIT for RESTART. Direct mode now targets a 2 GiB page cache and transactions bounded by 1,024 blocks / approximately 512 MiB / eight seconds. Background indexing keeps its 256 MiB cache and existing catch-up limits. Chain WAL remains synced, SQLite is WAL/NORMAL, and SQL rows never prune. A guard commits pending SQL records before their source blocks expire; failed catch-up refuses that chain advance.

With GPU verification, 60-second retention and 20 rounds, the larger direct batch/cache measured 153,721 aggregate TPS, 147,928 TPS over the last five rounds, and a 141,905 TPS minimum. The previous smaller-batch gated run measured 84,696 and 62,036 TPS respectively. This is a combined tuning comparison, not an isolation of cache size from transaction size. Final SQL flush is outside per-round TPS, and larger batches increase reader-visible indexing delay. Sustained 200,000 TPS is not achieved. See the full baseline and comparison and short-run experiments, including rejected changes.

The pruning guard is covered by timestamp-jump, retry, follower and process-exit tests. Process-exit tests do not simulate power loss or strengthen WAL/NORMAL durability. Larger batches remain bounded by the pruning guard when a shorter retention window is selected; the eight-second threshold is not a hard timer.

Direct SQLite writes and batch diagnosis (2026-10-24)

At the user's request, make stresstest2 now selects direct SQLite writes from block production/import. Bare sfc run retains its background writer; the direct flag is --sqlite-direct. SQLite OFF still disables indexing entirely. Direct mode has no block-job queue or separate SQL writer. The producer waits for SQL, and records cumulative microsecond timings in sqlite-write-profile.json. A failed index operation reports an error and retries its cursor; it cannot roll back an already authoritative RocksDB commit.

A 10-round, 1,048,576-transfer-per-round diagnostic with one SQLite COMMIT per block measured 27,497 committed TPS, falling to 20,585 TPS over the last five rounds (minimum 16,895). SQLite contained all 10,485,761 transactions, including the initial funding transaction; skipped pruned blocks and index errors were both zero. This contrasts with the much higher asynchronous chain TPS measurements below, whose SQLite ingestion was incomplete.

The longest SQLite COMMIT was 1.999 seconds. A 3-second stack sample confirmed sqlite3WalDefaultHook → sqlite3WalCheckpoint → fsync on the producer path. The run included sampling and lightweight phase profiling; it is diagnostic, not an isolated steady-state benchmark. WAL was enabled, SQLite rows were not pruned, and RocksDB retained its synced WAL and 60-second pruning.

The next candidate executes INSERTs directly but groups COMMIT across up to 16 blocks, approximately 8 MiB or 100 ms. Thresholds are checked after each block, including empty blocks; there is no independent 100 ms timer or hard latency bound. Clean shutdown also commits the remainder. One large block remains atomic. Rows and durable cursors publish together. Uncommitted rows are invisible to other SQLite connections. Tests cover direct error recovery, complete batch rollback/replay, explicit flush, shutdown flush, and restart. The comparison uses the same 256 MiB checkpoint trigger and 64 MiB cache.

The corrected batching candidate was subsequently measured with 5-second retention in the checkpoint comparison below; it did not reach the target. An earlier batch trial was stopped after discovering redundant per-block SAVEPOINTs and premature empty-block commits; those have been removed. Its partial results are excluded from the completed-run comparisons. The sustained 200,000 TPS target with complete SQLite indexing remains open.

Completed SQLite diagnostic runs are included in sustained-tps-2026-10-24.csv, with distinct sqlite-append, sqlite-checkpoint, sqlite-rayon-queue and sqlite-direct candidate names. sqlite-direct is the 10-round per-block COMMIT run, not the later batching candidate.

Moving checkpoints alone improved this sequential comparison but allowed the WAL to grow throughout the PASSIVE-only run. The current direct writer checks the WAL every 250 ms after its physical file reaches 256 MiB, uses PASSIVE, and additionally attempts RESTART at approximately 512 MiB of active frames. The measured peak is not a hard WAL limit, especially with long-lived readers. It still misses 200,000 TPS.

The bundled SQLite engine was upgraded from 3.50.2 to 3.51.3 before introducing concurrent checkpointing, fixing SQLite's documented WAL-reset race. Thus this is a candidate comparison, not an isolated estimate of thread placement alone. INSERT/COMMIT remain on the node thread. Shutdown joins the checkpoint worker; an exited worker restores automatic checkpoints at the next flush and exposes a health error. Tests cover an active reader snapshot, concurrent inserts, checkpoint progress, exact rows after restart and SQLite integrity. Further investigation is needed into per-transaction index writes and late-run throughput.

SQLite append-only and asynchronous writer investigation (2026-10-24)

make stresstest now defaults to SQLite OFF; make stresstest2 runs the same workload with SQLite ON. STRESS_ROUNDS=50 makes either run finite; zero remains continuous. Both retain the existing GPU, 60-second RocksDB pruning and durable WAL settings.

SQLite block/transaction/receipt/log rows no longer expire. The writer uses WAL with NORMAL synchronization, prepared statements and atomic batch cursor/count updates. A block commit sends only a nonblocking coalesced notification. The SQLite worker reads from its durable cursor without acquiring the execution mutex. Notification count is not a job count; a full one-slot queue already represents pending work. A 100 ms fallback also discovers log-only updates. A regression test holds a SQLite write transaction open while 40 blocks commit, then verifies complete catch-up and restart without duplicate rows.

The indexer lagged behind the 60-second block window; append-only means already indexed rows are retained, not that all committed transactions were indexed. The skipped-block counter makes that gap visible. The first candidate included a 5-second stack sample and is diagnostic. A dedicated two-thread Rayon pool for block/receipt row preparation and the nonblocking notification queue did not materially increase indexed transaction count in this sequential comparison. The last-20-round chain rate passed 200,000 TPS, but individual rounds still dipped below it and indexing remained incomplete. SQL INSERT/COMMIT remain on one writer: WAL permits concurrent readers but only one writer at a time (SQLite WAL concurrency). The queue does not store an unbounded copy of blocks, and it does not promise replay of blocks that expired before indexing. NORMAL retains the existing power-loss tradeoff: recent index commits may be lost, and only retained source records can be rebuilt.

Sustained 200,000 TPS investigation (2026-10-24)

The target is sustained committed throughput after retention starts, with GPU verification, SQLite ON, 60-second retention and synced RocksDB WAL. An early peak or a whole-run average above 200,000 TPS is not sufficient evidence.

The current storage layout isolates block values in a blocks column family and uses 35-byte binary receipt keys with 8-byte height values. Schema version 4 migrates existing blocks in restartable, synced batches; old hexadecimal receipt indexes remain readable. A single atomic WAL batch still commits the block, state, head and receipt indexes across column families.

The retention worker now durably deletes expired blocks and advances its floor. Receipt lookups require the referenced block to exist. Compaction reclaims stale receipt indexes below the durable floor, avoiding one random tombstone per expired transaction. Physical index reclamation follows compaction rather than a strict 60-second disk-space deadline. Block snapshots remain available through the separate block column family.

A late-run stack sample identified foreground RocksDB skip-list insertion as a major commit cost. Most sampled fsync calls belonged to the asynchronous SQLite thread, so their total cannot be attributed to foreground WAL latency. Smaller index memtables and alternative insertion strategies are being measured.

Dedicated bounded retention worker (2026-10-24)

The server now starts one sfc-retention thread. It owns an Arc<Store> and never acquires the node/admission mutex. Each pass deletes up to four blocks or reaches approximately 1 MiB of deletion records (a single block remains atomic, so the byte threshold can be exceeded by that block), then waits 5 ms before more backlog work. When caught up it waits 50 ms. There is no per-block job queue.

The worker copies the head and releases its read lock before pruning. An internal prune mutex serializes cleanup only; production skips it while the worker is active. Segment cleanup releases the projection-writer lock before filesystem I/O. Foreground block commit and history projection remain ordered and synchronous; WAL sync, signature verification, execution and SQLite indexing are unchanged. This removes expiration work from the node lock but does not eliminate shared RocksDB writer serialization or shared-disk contention.

Deletion batches still atomically remove blocks and receipt indexes with a synced WAL. The earliest-history hint advances only after success. An unfinished bounded pass does not mark its cutoff complete. Receipt lookups now read their hash index and block from the same RocksDB snapshot. Startup drains outstanding expiry and repairs history; direct library users retain synchronous maintain() unless they explicitly start a worker. Server shutdown signals and joins the worker. A worker I/O error or panic reaches the server's main select loop and stops the server.

Physical expiry is asynchronous and can lag under load. Dashboard storage stats expose retention_worker_active, retained_history_floor, and retention_completed_cutoff. These are individual observations, not an atomic snapshot of all dashboard fields. They allow operators to detect cleanup backlog.

Fresh-DB slowdown diagnosis (2026-10-24)

Resetting the actual default stress DB did not remove the sustained slowdown. With the retained-history scan fix, 25 rounds averaged 198,260 TPS: rounds 1–10 averaged 256,585 TPS, while rounds 11–25 averaged 172,169 TPS. These averages are total transfers divided by total measured time.

A separate 25-round diagnostic run instrumented Node::produce and sampled its stacks. The first and last 1,000 produced blocks had these cumulative costs:

Work First 1,000 blocks Last 1,000 blocks
Transactions in those blocks 1,888,257 2,138,112
Execution/building the block 2.067 s 2.364 s
Durable commit 2.140 s 7.919 s
Pending revalidation/bookkeeping 0.042 s 0.048 s
History projection and pruning 0.063 s 3.369 s

Execution cost per transaction stayed close to constant. Commit and maintenance costs grew sharply; the longest maintenance call took 1.403 s. Stack samples identified prune_at → WriteBatch → MemTableInserter::DeleteCF and skip-list insertion: expiry deletes one randomly keyed receipt index per transaction. Node::produce holds the shared node mutex through maintenance, so these pauses also block transaction admission. The earlier scan fix avoids revisiting deleted blocks, but does not remove this per-receipt deletion work.

The reset run's RocksDB log recorded 159 compactions, 29.224 GB of compaction output, and 92.290 s of summed compaction job time. This is background job time, not a measurement of foreground stall time. Block values and random receipt indexes share one column family; compaction, synced WAL writes, history projection and asynchronous SQLite indexing share the disk. Stack samples confirm deletion/compaction/sync activity but do not establish an exact percentage of lost throughput attributable to each subsystem.

Larger-buffer comparison (rejected)

A fresh 25-round run increased the RocksDB write buffer from 64 to 256 MiB and the base level size from 256 MiB to 1 GiB. It reduced compaction output to 17.289 GB across 28 jobs, but did not improve sustained throughput:

These are sequential diagnostic runs, not an interleaved statistical comparison. The larger-buffer settings were reverted; no unproven tuning remains in storage. Raw round metrics: storage-slowdown-2026-10-24.csv.

The remaining design issue is the cost of random per-transaction expiry while holding the node lock, combined with durable commit I/O. Reducing compaction bytes alone did not fix it. A structural follow-up should evaluate partitioning receipt indexes by retention window so expiry can remove bounded ranges/segments, while preserving receipt lookups, atomic commit, snapshots and crash recovery. Moving maintenance out of the lock by itself is insufficient: prior trials increased admission retries and pending revalidation. Sustained 200,000 TPS remains unachieved; the timing instrumentation was removed after diagnosis.

Retained-history scan fix (2026-10-24)

A persistent stress run exposed a pruning regression hidden by fresh, short runs. After the 60-second retention boundary, each maintenance pass sought from the beginning of block/. RocksDB had to traverse and decompress deleted SST records until background compaction removed them. Stack sampling identified this seek path; individual maintenance pauses reached roughly 350–456 ms while block execution was normally around 4–5 ms.

Storage now remembers a lower bound for retained history, advances it only after successful durable deletion, and reconstructs it on open. Pruning, history lists, earliest-height reads and indexer snapshots start at that bound. The indexer loads the bound before taking its snapshot so it cannot skip records retained by an older snapshot. A completed retention cutoff is checked once per block timestamp second; failed cleanup remains retryable. Receipt deletion uses fixed-width keys. The synced WAL, 60-second retention, block limits and SQLite indexing remain enabled. No storage schema or serialized block format changes are required.

Current optimization comparison (2026-10-20)

The current ordered-state implementation was compared with the runtime before this optimization, on the same macOS arm64 host using Rust 1.99.0, release/thin LTO and 18 Rayon workers. Three trials alternate before/after order. Values below are medians of the three runs; signatures are generated before timing. Each run uses 81,920 native transfers, 20 blocks of 4,096 transactions, and three accounts. The baseline includes the preceding correctness fixes and ordered EVM database. There was no existing Git commit to identify it: this repository was an initial staged snapshot, and the pre-optimization executable was retained for comparison. Raw data: speed-comparison-2026-10-20.jsonl.

The full Rayon path's median block p50 fell from 50.84 ms to 28.08 ms. It includes signature checks, admission execution, block execution, RocksDB WAL/fsync, JSONL fsync and maintenance. The live benchmark uses two Python-supervised release nodes, 100-item HTTP batches over a persistent connection, 16,384 signed native transfers, and a 100 ms block interval. Timing ends when the follower exposes the final durable receipt, and includes admission, scheduling and HTTP/3 replay. It validates matching blocks, exact nonce/balance and no restarts. Contract deployment is warm-up; signing and process startup are outside timing. This is a short local burst, not sustained multi-machine capacity or BFT consensus. Newly initialized nodes and supervised networks now use 100 ms by default, a 40,960 tx/s transaction-count ceiling at 4,096 tx/block. Existing configurations are preserved; a retained 500 ms interval still caps them at 8,192 tx/s. To adopt the tested setting, set block_interval_ms to 100 in the existing config and restart the node. Faster cadence increases empty-block writes and history growth; this setting is a scheduling target, not a distributed-finality guarantee.

Rayon is used for synced-block verification, HTTP JSON-RPC transaction batches, and the library's Node::submit_batch. Single submissions remain serial. Batches below 32 items skip parallel scheduling. Larger indexed batches preserve order; strict import reports the first invalid transaction in input order. EVM execution and durable state mutation stay sequential. Tests compare receipts/state roots on 1, 2 and 4 workers, plus malformed batches, notifications and HTTP/3 replay.

The default pool uses available CPU parallelism. Tune it for the host:

RAYON_NUM_THREADS=4 make run
RAYON_NUM_THREADS=4 SFC_BENCH_BATCH=4096 SFC_BENCH_BLOCKS=100 make bench

There is no guarantee that more workers always give better latency or throughput. The implementation uses Rayon's indexed iterators.

At that historical cadence, the transaction-count ceiling was 8,192 tx/s (4,096 / 0.5 seconds), before gas, data, network or CPU constraints. This is a configuration ceiling, not measured sustained live-chain throughput. Contract-heavy blocks hit the gas ceiling sooner. Raising limits requires realistic workload tests.

Optimizations made

  • Optimized libsecp256k1 recovery: roughly 13,628 to 64,176 checks/s in separate local runs.
  • Cached pending EVM state avoids replaying the entire queue for each admission.
  • Hash-set duplicate detection and byte/count-bounded admission.
  • One-pass candidate selection and block execution, instead of executing candidates twice.
  • In-memory current state; differential JSON account writes in atomic RocksDB batches.
  • Indexed receipt lookup; pruning removes the associated indexes.
  • Incremental pruning instead of scanning all historical blocks every tick.
  • Hourly append-only JSONL segments instead of per-block files and directory fsyncs.
  • HTTP/3 persistent RPC connections, bounded streaming buffers and batched block fetches.
  • Release-mode run target, thin LTO and one code-generation unit.

The earlier 100-transfer durable-path run measured 11,613 tx/s; this rerun measured 20,565 tx/s. These are before/after observations, not controlled repeated experiments. Fsync is enabled in both; durability was not disabled to improve the number.

The current harness uses native transfers and a small fixed state. Next performance gates are ERC-20-heavy mixes, growing account/storage sets, sustained network load, slow disks, loss/latency, recovery and validator failures. Whole-state commitment, state copying/loading, single-writer admission, and startup projection reconstruction remain scaling limits. Do not infer production capacity or external-L1 parity from these results.
