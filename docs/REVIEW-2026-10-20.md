# Rust blockchain review — 2026-10-20

Scope: the initial staged snapshot and accompanying fixes. `main` has no commits
yet, so there is no commit SHA to certify. Tests ran locally on macOS arm64. This
is a code/design review, not a consensus proof or Ethereum conformance audit.

## Assessment

The execution core is structured for deterministic replay and passes the exercised
workloads. The network is a development sequencer plus replaying followers, without
distributed BFT finality. It is a useful starting point for a Rust application
behind CometBFT, but does not replace CometBFT plus the Cosmos SDK today.

## Fixed defects

1. `RoundLock::apply_prevote_certificate` forgot the certificate round when a nil
   certificate cleared the lock, allowing an older certificate to restore an
   obsolete lock. The highest certificate round now survives unlock and
   serialization. Older and same-round conflicting certificates are rejected;
   identical certificates remain idempotent. Old serialized locks missing this
   field are rejected because their forgotten history cannot be recovered. This
   changes the library's lock snapshot format, not the node's chain database.
2. RPC `eth_call` and `eth_estimateGas` applied EIP-3607 and rejected callers with
   deployed code. A separate simulation path disables that check without changing
   caller identity or committing state. Transaction execution, including strict
   dry runs, retains the check. Regression tests verify CALLER, storage isolation,
   gas estimation, and continued transaction rejection.

## Significant design gaps

These are blockers for production validator/application use, including documented
limitations; they are not claims that explicit development mode promised BFT.

| Priority | Code | Consequence and next change |
| --- | --- | --- |
| P1 before BFT deployment | `node.rs::produce/import`, `main.rs::run`, `consensus.rs` | Blocks commit without validator certificates. No proposer election, round reactor, vote gossip, validator-set lifecycle, consensus WAL integration or leader failover exists. A trusted sequencer can equivocate between followers. Integrate a consensus engine before claiming finality. |
| P1 before SDK-style composition | `framework.rs::Module` | Hooks receive the entire mutable `World`, including balances and block hashes. There is no scoped store authority or hook resource meter, and Rust hooks can consult external state. Introduce scoped stores, narrow capabilities, deterministic context, resource accounting and module migrations. |
| P2 scalability | `framework.rs::execute`, `ethereum.rs::load_db/save_db`, `types.rs::World::root`, `node.rs::produce` | Empty blocks still clone/load/serialize whole state. Account-level delta writes do not remove this cost. Admission executes transactions, production executes them again, and remaining pending entries are replayed each block. Use database-backed overlays, fine-grained dirty records, incremental authenticated commitments and bounded rechecks. |
| P2 recovery | `storage.rs::repair_history` | Startup collects all retained blocks and serialized history segments in memory. Large archives can fail to restart despite a healthy database. Stream repair through bounded buffers while preserving atomic replacement and directory sync. |
| P2 responsiveness | `network.rs::PeerServer`, `rpc.rs::handle` | Peer handlers execute synchronous work on the sole async runtime thread. HTTP simulations hold the global mutex, and blocking HTTP work lacks an explicit concurrency admission limit. Use bounded queues, move peer work off the event loop and provide immutable read snapshots. |
| P2 protocol evolution | `types.rs::World::root/Block::hash/Genesis` | Hashes depend on Rust-struct JSON encoding; genesis does not bind application/module versions. Identical builds are stable, but schema/serializer or module changes can fork replay without an upgrade protocol. Specify canonical bytes and versioned, height-gated migrations. |

Followers cannot bootstrap past pruned history without an archive peer. Verified
state snapshots are also needed for scalable synchronization. Loopback-only
listeners and zero PREVRANDAO remain intentional development constraints.

## Determinism evidence and limits

Owned state uses ordered maps; EVM changes are sorted before persistence; execution
uses integer arithmetic; transaction/log ordering is explicit; Rayon results are
collected in input order; block time is an input to replay. Wall-clock logging and
floating-point dashboard rates do not affect commitments. Independent sequencers
can propose different timestamps/orderings: compare execution of the same agreed
block, not independently produced chains.

Tests compare insertion orders, 1/2/4 Rayon workers, strict import versus production
and separate processes. The new fixed-vector test executes TIMESTAMP, NUMBER,
CHAINID and BLOCKHASH at distances 1/256/257 after pruning and reopening the DB.
It checks opcode results and final state/block hashes in debug and release builds.
These are regression vectors, not external Ethereum conformance vectors.

Still needed: those vectors on x86-64/Linux and other supported platforms, upstream
EVM state tests, malformed-input fuzzing, dependency-upgrade replay, module purity
tests and adversarial consensus simulations. Banning selected source identifiers
is a regression guard, not proof of dependency or module determinism.

## CometBFT and Cosmos SDK direction

Recommended architecture: **CometBFT → ABCI application in Rust → scoped modules +
REVM + authenticated storage**. Preserve disposable proposal state, deterministic
validation/finalization, and a consensus-directed durable commit boundary. Recovery
must reconcile application height/hash with CometBFT; direct `Node::produce` is not
an ABCI adapter. See [ABCI lifecycle and determinism requirements](https://github.com/cometbft/cometbft/blob/main/spec/abci/abci%2B%2B_basic_concepts.md).

The SDK comparison is architectural. Cosmos keepers restrict access to module
state; SFC currently provides lifecycle callbacks without that capability model
or the existing SDK module ecosystem. A Rust ABCI application need not use the Go
SDK but must implement the application services it needs. See [Cosmos SDK keepers](https://docs.cosmos.network/sdk/v0.53/build/building-modules/keeper).

Two replicas test replay/recovery, not Byzantine tolerance. Four equal validators
are the minimum to tolerate one Byzantine validator under the usual less-than-one-
third voting-power assumption. The four processes tested here remain one sequencer
and three followers. See [CometBFT consensus](https://github.com/cometbft/cometbft/blob/main/spec/consensus/consensus.md).

## Apple MLX

MLX provides array/ML execution on CPU/GPU with shared memory on Apple silicon. It
is not a drop-in backend for REVM, secp256k1 recovery, Keccak or RocksDB. Based on
this code, removing whole-state work and lock contention deserves priority. No MLX
speedup had been measured at review time. The subsequent
[integer-only MLX/Metal recovery experiment](MLX-ECDSA.md) passes differential tests
but is substantially slower than the existing parallel CPU verifier. The node
continues to use CPU verification. See [the official MLX project](https://github.com/ml-explore/mlx).

Plausible experiments are off-chain anomaly detection, log analysis and workload
forecasting. Keep model output out of block validity/state transitions: MLX
documents numerical differences depending on backend, hardware and algorithm/batch
selection. A fixed random seed does not guarantee identical validator execution.
See [MLX numerical precision](https://ml-explore.github.io/mlx/build/html/usage/precision.html).

If cryptography becomes a measured bottleneck, benchmark CPU/Rayon batching first.
Experimental integer GPU cryptography would need a separately audited algorithm,
deterministic CPU verification/fallback, and measurements including batching/launch
overhead. No GPU benefit has been established for this implementation.

## Validation

```sh
make check integration test-two-nodes test-service
cargo test --locked --test determinism
cargo test --locked --release --test determinism --test parallel
```

The full checks passed: formatting/Clippy, Rust tests, HTTP/3 and TCP sync, TLS
rejection, JSON-RPC framing, Solidity ERC-20 deployment/transfers/approval/reverts/
events, batch admission, pruning/archive transitions, release build and background
service lifecycle. The added fixed-vector test passed afterward in both profiles.

`make test-two-nodes` builds the node, installs pinned fixture dependencies and runs
`scripts/test_supervisor.py --nodes 2`. Python owns all node processes; the JS helper
only generates signed bytes. Two-node and four-node runs each passed 34 legacy/
type-2 transactions with matching historical block hashes/state roots/receipts,
balances, nonces, contract storage, simulations, replay/read-only rejection,
follower/sequencer kills and restarts, persistent network restart, restart limits
and process cleanup. These are local tests, not WAN-partition, Byzantine-validator,
sustained-load or power-failure tests.
