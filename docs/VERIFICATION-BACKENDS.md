# CPU, GPU and HYBRID node verification

The default GPU runtime is **native Rust/MLX** (`mlx-native`), calling Apple’s
MLX C API in-process without a Python process or GPU IPC. The MLX measurements below are historical; they do not
measure the current default. The same exact-integer kernels are compiled with
constants generated by Rust at build time. MLX builds a lazy graph of GPU arrays; only the final result is evaluated and read
on CPU. MLX’s allocator caches intermediate buffers. Input staging entails one
copy into an MLX-owned array; this is not an end-to-end zero-copy claim.
The separate `metal` runtime retains the direct Metal implementation for comparison.

The development node supports all three transaction authentication modes. **GPU is
the default**, including configurations that omit the `verification` object.
This applies to single and batched transaction submission and follower block replay.
EVM execution, state updates, hashing, storage and EVM precompiles still run on CPU.
The topology remains a sequencer plus verifying followers, without distributed BFT.

## Selecting a backend

```sh
make release
./target/release/sfc init --home .sfc-v3
./target/release/sfc run --config .sfc-v3/config.capnp                       # GPU
./target/release/sfc run --config .sfc-v3/config.capnp --verification-backend cpu
./target/release/sfc run --config .sfc-v3/config.capnp --verification-backend hybrid

# Applies to nodes started by the Python service/supervisor too:
SFC_VERIFICATION_BACKEND=cpu make testnet
python3 scripts/supervisor.py --nodes 2 --verification-backend hybrid
```

Precedence is run CLI flag, `SFC_VERIFICATION_BACKEND`, then persisted configuration.
`init --verification-backend cpu` creates an explicitly CPU-configured home.
Edit `config.capnp` using the Python codec described in [binary tooling](CAPNP-V3.md). The equivalent in-memory configuration is:

```python
verification = {
  "backend": "gpu",
  "gpu_runtime": "mlx-native",
  "python": "/absolute/path/to/SuperFrontierChain/target/mlx-venv/bin/python",
  "worker": "/absolute/path/to/SuperFrontierChain/experiments/mlx_ecdsa/worker.py",
  "timeout_seconds": 30
}
```

The `python`/`worker` paths are used only when explicitly selecting the legacy
`gpu_runtime: "mlx"` research worker. All default modes run without Python.
GPU and HYBRID require Apple Metal; startup fails clearly if unavailable.
Ubuntu CI explicitly selects CPU. Existing configurations that omit `gpu_runtime`
select native MLX when initialized, without changing chain commitments or database data.

`CPU` uses libsecp256k1 and ordered Rayon batches. `GPU` dispatches all parsed recovery
records into MLX arrays and custom Metal kernels. `HYBRID` concurrently sends the first 40% to GPU
and the remaining 60% to CPU, then merges the actual recovered keys in input order.
Singleton HYBRID work goes to GPU; a batch of two or more uses both processors.

```sh
curl -s http://127.0.0.1:8545/ -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"sfc_verificationStatus","params":[]}'
```

Status includes the effective backend, GPU runtime, Rust/worker PIDs and CPU/GPU
record counters. Native MLX reports `gpu_runtime: "mlx-native"` and `gpu_worker_pid: null`.
Counters count completed recovery attempts, including transactions subsequently
rejected by admission (for example a full mempool). Startup self-tests are excluded.
Counters reset when a node restarts. They are diagnostics and never enter state roots.

## Ordering, correctness and failures

All paths share canonical RLP, chain ID, low-S and parity checks. The GPU kernel uses
exact integer modular arithmetic. Recovery results preserve input order regardless
of GPU/CPU completion timing. Admission and EVM execution remain sequential.
Malformed individual transactions retain their own error slots. Batch resource-limit
failures and worker/protocol failures reject the authentication batch before admission.

The native verifier runs valid/invalid startup vectors against the CPU reference.
It waits for Metal completion before reading shared outputs and never reuses a
timed-out command's buffers. Dispatch failures discard the engine; a subsequent
request initializes a fresh engine. There is no silent CPU fallback.

Only the optional legacy worker uses the following protocol: length-framed Cap’n Proto with binary signatures and public keys. It checks request IDs, response counts, bounded message sizes
and public-key encodings. Every worker startup executes valid/invalid GPU vectors
against a CPU reference. Read/write socket operations time out (30 seconds by default;
configurable 1–120 seconds). Any failed exchange discards and reaps the worker, so a
late response cannot authenticate a different batch. A subsequent request starts a
fresh worker. There is **no silent CPU fallback**, including in HYBRID. A failed
follower verification leaves that block uncommitted and the sync loop retries.
Workers exit on parent socket EOF; normal node shutdown kills and reaps its worker.

Tests compare CPU/GPU/HYBRID sender addresses, hashes, acceptance, exact blocks,
receipts and state roots, including repeated mixed-validity batches of up to 4,096
records. Separate kernel differential tests cover 65,829 recovery vectors, 33,568
arithmetic comparisons and 10,008 GLV decomposition cases. This is tested consistency
on the available Apple hardware/software, not a cryptographic audit or a proof across
all devices. The experimental worker and kernels are trusted local code.

## Rust-only benchmarks

```sh
make benchmark                  # release, GPU, 262144 transfers, SQLite ON/OFF × 3
make bench-network              # same benchmark, sequencer plus TCP follower
make bench-backends             # CPU, GPU, HYBRID
make stresstest                 # persistent one-node GPU run until make stop
make stop
make test-stresstest            # Rust stop/restart/crash/index/two-node tests
make test-verification          # native GPU vs CPU differential checks
```

These commands use `sfc-bench`, a Rust executable. It generates signed transactions,
manages child nodes, submits typed Capnp RPC batches over TCP or HTTP/3, measures committed TPS and cumulative
process CPU time, and writes length-framed Cap’n Proto reports. No Python or Node.js
process participates. `--gpu-runtime mlx-native|metal` selects native MLX or direct
Metal. The Python GPU worker has been removed from the node. Old `mlx` settings
are automatically migrated to `mlx-native`; retained `python`/`worker` path fields
are inert compatibility metadata and are never executed. `--sync-transport tcp|http3`
selects follower synchronization, with Cap’n Proto RPC over TCP as the default. Historical Python research under `experiments/` remains reference material only; old
`bench-mlx*` Make targets now route to the Rust benchmarks.

Signing, node startup and warm-up occur before timing. CPU 100% means one logical
core, measured across all Rust node threads (both nodes for the two-node benchmark).
The Rust load generator is excluded. GPU utilization and energy are not measured.
Balances, nonces, verification counters and replicated block equality are asserted.
SQLite ON trials also check index catch-up after the committed-TPS interval.
The benchmark rejects child-node failure rather than reporting a successful run.
Results default to `target/rust-benchmark.capnp`; stress results append under
`.sfc-stress-v3/results.capnp`. `make stop` retains chain data.

Use `BENCH_TRANSACTIONS`, `BENCH_REPEAT`, `BENCH_SQLITE=on|off|both`,
`BENCH_BACKEND=cpu|gpu|hybrid` and `STRESS_THREADS` to configure finite benchmarks.
Stress runs retain `STRESS_DIR`, `STRESS_TRANSACTIONS`, `STRESS_BATCH`,
`STRESS_INTERVAL` and `STRESS_SQLITE=on|off`.

Apple M5 Max, release build, one node, GPU, 12 Rayon threads, 10 ms interval,
262,144 transfers, 4,096 requests/batch; five alternating trials per SQLite mode:

| SQLite | Median committed TPS | Median node CPU | Median CPU µs/tx |
| --- | ---: | ---: | ---: |
| ON | 148,635 | 220.2% | 14.80 |
| OFF | 160,484 | 141.3% | 8.71 |

Report: `target/native-rust-benchmark.capnp`. ON index catch-up took a further

Both the load generator and GPU host changed from the historical Python benchmark;

## Historical MLX two-node TPS and CPU measurement

Hardware: Apple M5 Max, 18 logical CPUs, macOS 27.0.1, MLX 0.32.4. Release builds;
two local processes connected through certificate-pinned HTTP/3. A signed fixture
alternates legacy/type-2 native transfers. Contract deployment/call warms up the
chain before timing. The timed phase includes HTTP admission, signatures, ordered
EVM execution, synchronous RocksDB WAL commits, network replay and follower commit.
The ending receipt, balances, nonces and block/state-root agreement are checked.
This measures committed replicated TPS, not signature recoveries per second.

Three trials rotate backend order. Each larger-batch trial submits 65,536 transfers
in RPC batches of 4,096, using the default 100 ms block interval, 4,096 transactions
per block and 16,384-slot mempool. The RPC boundary now accepts at most 4,096 requests
and a 5 MiB JSON body; raw transaction batch bytes remain limited to 2 MiB.
Normal mempool backpressure retries only rejected entries; retry verification and
waiting are included in timing and CPU cost. The raw report records attempts, since
faster admission can cause more retries. This is a short burst benchmark, not a
long-duration stress test or a signature-only comparison at equal recovery counts.

CPU usage is cumulative process user+system CPU time across **both Rust nodes plus
both MLX workers**. 100% means one CPU core, not the entire machine. The Python load
generator is reported separately and excluded. macOS `ps` exposes 10 ms CPU-time
resolution. CPU samples bracket the measured interval, adding small sampling overhead.
GPU utilization, watts and energy are not measured.

**4,096 requests/batch; 65,536 committed transfers** (medians of three trials):

| Mode | Committed TPS | TPS range | Total host CPU | CPU ms/committed tx |
| --- | ---: | ---: | ---: | ---: |
| CPU | 39,227 | 39,158–39,349 | 370.5% | 0.0943 |
| GPU | 38,180 | 37,546–39,809 | 116.3% | 0.0301 |
| HYBRID | 38,758 | 38,474–40,212 | 246.0% | 0.0632 |

**100 requests/batch; 16,384 committed transfers** (medians of three trials):

| Mode | Committed TPS | TPS range | Total host CPU | CPU ms/committed tx |
| --- | ---: | ---: | ---: | ---: |
| CPU | 29,877 | 28,714–29,993 | 247.1% | 0.0830 |
| GPU | 9,594 | 9,582–9,606 | 46.8% | 0.0488 |
| HYBRID | 8,929 | 8,875–8,963 | 84.5% | 0.0952 |


The configured block cadence and size target a 40,960 TPS ceiling. Larger batches
approach that ceiling, so these measurements do not establish maximum verifier
throughput. GPU reduces host CPU substantially while giving similar large-batch TPS;
it is not universally faster. Small batches pay dispatch and IPC overhead and do
not fill the GPU sufficiently. Higher throughput requires changing the block/cadence
limits and then measuring execution, storage and replay again.

The earlier 841,333 GPU recoveries/sec figure is a 65,536-signature microbenchmark;
it does not represent node TPS. Node recovery batches are bounded to 4,096.

## Capnp v3 throughput tuning (2026-10-20)

The release GPU path now decodes Ethereum RPC hex in parallel, transfers ownership
of the decoded bytes into shared buffers, and derives sender addresses in parallel
after GPU recovery. Indexed collection preserves request order, including malformed
entries. Admission and EVM state mutation remain ordered; signature checks and
synchronous RocksDB commits are unchanged.

On the development Apple Silicon host, alternating three before/after runs of
65,536 transfers (one node, 4,096 requests/batch, 10 ms, 12 Rayon threads) yielded
median 113,817 -> 125,098 committed TPS. CPU increased from 159.8% to 186.4%.
CPU 100% means one logical core; Rust and the MLX host are included, the load
generator is excluded. These are speed optimizations, not a CPU reduction claim.

The highest short-run observation was 128,901 TPS at 5 ms. Longer 262,144-transfer
trials favored 10 ms / 12 threads: median 127,675 TPS and CPU 188.5%, with a
102,338–128,106 TPS range. The 5 ms and automatic-thread trials varied more.
These local transfer workloads are not a sustained throughput guarantee,
multi-validator BFT finality measurement, or arbitrary-contract benchmark.

`make stresstest` therefore defaults to `STRESS_INTERVAL=10 STRESS_THREADS=12`.
Both knobs are configurable; 1–2 ms intervals were slower in the measured runs.
To reproduce longer trials:

```sh
RAYON_NUM_THREADS=12 python3 scripts/benchmark_network.py \
  --nodes 1 --backend gpu --rpc-batch 4096 --transactions 262144 \
  --interval 10 --repeat 3 --output target/throughput.capnp
make test-benchmark-metrics test-fixture test-migrations
make test-stresstest test-verification
```

Signing is prepared before timing and bounded to 4,096 concurrent jobs. Reports
include binary/source hashes, CPU process-time deltas, GPU routing counters and
commit checks. Never interpret a signature-recovery microbenchmark as chain TPS.

## Storage and index batching (2026-10-20)

History projections now reuse their hourly file and amortize syncs at 100 ms or
8 MiB during maintenance; RocksDB still synchronously commits each block. The
transaction index reuses a single encoded block height for all receipts in that
block. SQLite catch-up batches at most 16 blocks or approximately 8 MiB and uses
a 4,096-page automatic WAL checkpoint threshold. A single oversized block remains
atomic; these limits are checked after adding each block.

Three alternating before/after release GPU trials on this development host used
262,144 transfers, one node, 4,096-request batches, 10 ms and 12 Rayon threads:

| Median measurement | Before | After |
| --- | ---: | ---: |
| Committed TPS | 127,152 | 138,707 |
| Rust + MLX host CPU (100% = one core) | 191.1% | 214.1% |
| CPU time per committed transfer | 14.95 µs | 15.45 µs |
| Additional SQLite catch-up after commit checks | 2.415 s | 0.497 s |

Committed throughput increased 9.1%; additional indexing delay fell 79.4%.
The optimized trials ranged from 138,594 to 139,043 TPS. CPU utilization increased;
the indexer also completed more work during the commit measurement window.
Catch-up time is measured separately after balance/nonce/backend validation and
does not enter the committed TPS calculation. All 262,146 transactions, including
the two warmups, were indexed in each run.

These are short local transfer workloads with few accounts, not sustained
capacity, general-contract throughput or BFT finality. Full-state loading,
cloning and hashing remain scaling bottlenecks. The new batching does not change
the chain protocol, hashes, execution order or signature verification.

Reproduce using a previously saved compatible fixture:

```sh
RAYON_NUM_THREADS=12 python3 scripts/benchmark_network.py \
  --nodes 1 --backend gpu --rpc-batch 4096 --transactions 262144 \
  --fixture target/tps-fixture-long.capnp --interval 10 --repeat 3 \
  --compare target/pre-io-opt-sfc --index-timeout 30 \
  --output target/io-optimization-comparison.capnp
```

Omit `--fixture` to prepare fresh signatures before timing, and omit `--compare`
to measure only the current binary. Both executable hashes are recorded per trial.

## Capnp / GPU IPC (2026-10-20)

The next optimization pre-sizes the Rust request arena and writes its segments
directly to the socket. A reusable buffer backs response readers. Python reads
into its request buffer, avoids concatenating framed responses, and returns
contiguous 17-word GPU result rows instead of creating a separate Python bytes
object and Capnp Data entry for each public key. MLX results are accessed with
`np.asarray`; Rust retains strict status/count/curve-point validation. Integer GPU
kernels and consensus bytes are unchanged. See [wire details](CAPNP-V3.md).

Three alternating trials using the same 262,144-transfer workload and configuration
as above compared the pre-IPC-optimization executable/worker against the new pair:

| Median measurement | Before | After |
| --- | ---: | ---: |
| Committed TPS | 138,864 | 142,158 |
| Rust + MLX host CPU (100% = one core) | 212.9% | 213.1% |
| CPU time per committed transfer | 15.45 µs | 14.99 µs |

Throughput increased 2.4%, with roughly unchanged CPU utilization and 3.0% less
measured CPU time per transfer. The optimized trials ranged from 141,680 to
142,326 TPS. These short, single-node observations are not a sustained capacity
claim or a GPU-kernel throughput benchmark. All transactions, balances, nonces,
GPU routing counters and SQLite index totals were checked.

```sh
RAYON_NUM_THREADS=12 python3 scripts/benchmark_network.py \
  --nodes 1 --backend gpu --rpc-batch 4096 --transactions 262144 \
  --fixture target/tps-fixture-long.capnp --interval 10 --repeat 3 \
  --compare target/pre-capnp-gpu-sfc \
  --baseline-gpu-worker target/pre-capnp-gpu/worker.py \
  --index-timeout 30 --output target/capnp-gpu-comparison.capnp
```

The baseline worker snapshot includes its original `recovery.py` and
`secp256k1.metal`. Preserve those files when reproducing the comparison.

## SQLite ON / OFF comparison (2026-10-20)

Five alternating runs per mode used the same release executable, Apple MLX GPU,
262,144 transfers, one node, 4,096-request batches, 10 ms blocks and 12 Rayon threads.
OFF skips creating the SQLite writer/thread entirely; RocksDB synchronous commits,
history projection and structured logs remain enabled in both modes.

| Median measurement | SQLite ON | SQLite OFF |
| --- | ---: | ---: |
| Committed TPS | 140,196 | 148,912 |
| Rust + MLX host CPU (100% = one core) | 212.6% | 131.2% |
| CPU time per committed transfer | 15.14 µs | 8.93 µs |
| CPU seconds during commit measurement | 3.97 s | 2.34 s |

OFF increased median TPS by 6.2%, reduced CPU utilization by 38.3%, and reduced
CPU time per transfer by 41.1%. ON ranged from 137,602–141,116 TPS; OFF ranged from
138,680–152,273 TPS. This is a short local workload with few accounts, not a
sustained capacity claim. The CPU metric includes all Rust and MLX host threads,
including concurrent indexing when ON, and excludes the load generator.

ON needed a median 0.495 seconds of additional catch-up after commit validation
to index all 262,146 transactions including warmups. That additional work is outside
the committed TPS/CPU window. OFF has no corresponding index output: explorer/log
search is unavailable. The comparison therefore quantifies the optional index's
cost, not equivalent feature sets.

The benchmark verified runtime flags, absence of all SQLite files when OFF,
balances, nonces, GPU routing and index totals when ON. `test_indexer_toggle.py`
also verifies catch-up after re-enabling, preservation of existing index bytes
while OFF, rejection of stale index queries, and continuing Ethereum receipts.

```sh
RAYON_NUM_THREADS=12 python3 scripts/benchmark_network.py \
  --nodes 1 --backend gpu --sqlite both --rpc-batch 4096 \
  --transactions 262144 --fixture target/tps-fixture-long.capnp \
  --interval 10 --repeat 5 --index-timeout 30 \
  --output target/sqlite-on-off-comparison.capnp
make test-indexer-toggle
```

To run continuously without the index, stop the current runner and start with
`make stresstest STRESS_SQLITE=off`. Starting with `STRESS_SQLITE=on` (the default)
resumes indexing retained records from saved cursors.

## Python process-management boundary

Python is allowed for supervisor lifecycle operations (start, stop, restart,
health/control messages and fault injection). GPU computation, transaction signing,
load generation, submission, TPS/CPU measurement, replay and persistence execute in
Rust. `make test-mlx` now runs native Rust MLX tests; `make mlx-setup` is a
compatibility alias for the Rust release build. No Python MLX package is installed.
The supervisor-only Capnp adapter uses `target/supervisor-venv`, with pycapnp only.
Legacy `scripts/benchmark_network.py` and `scripts/stresstest.py` are thin process
launchers that replace themselves with `sfc-bench`; they perform no benchmarking.
